# 2026-09-24 使用者走查：staging 版本全功能地毯式測試

> **一句話結論**：「打開 → 轉 → 出發」這條主線是順的，而且很快。問題幾乎都發生在**轉完之後**：
> app 不記得「今天決定吃哪裡」，也不知道「大家最後真的去吃了哪裡」。所以紀錄頁、不重複規則、
> 統計、團隊功能，全都建立在「轉了幾次」上，而不是「吃了哪幾餐」。這是這一輪最重要的發現，
> 後面大部分的問題都是它的後果。

## 0. 怎麼測的（先讀這段，決定這份報告能信多少）

**測的是什麼版本**：commit `813c874f`，和 `origin/staging` 完全相同。

**為什麼不是直接開 staging**：這個容器連不到 Vercel（proxy 403），而且 Google 登入只在正式部署的網域
能用。所以在本機架了一個 staging 複本：

| 部分 | 怎麼處理 | 和 staging 的差別 |
|---|---|---|
| 前端 + API | 真的程式碼，`pnpm dev` | 同一份 |
| 資料庫 | MariaDB 10.11，所有 migration 都有套用 | TiDB 會把 JSON 欄位直接解析成物件，MariaDB 給字串 → 已在測試環境補上解析（見下方「排除的假警報」） |
| Google Places | 假資料：內湖瑞光路附近 28 家店，**刻意放了雜訊**：中午沒開的早餐店、茶館、連鎖店、2.8 分的店、只有 1 則評論的 5.0 分店、暫停營業、永久歇業、12:25 就關的店、只開午餐的便當店 | 店名全部都有英文版（真的 Google 上很多小店只有中文名），所以「英文店名」的問題在這裡會被放大 |
| 時間 | server、DB、瀏覽器三個時鐘對齊在 **2026-09-24（四）12:05 台北** | — |
| 裝置 | 390×844、iPhone UA、瀏覽器語言 zh-TW、定位在辦公室 | 沒有真的手機鍵盤、沒有真的權限對話框 |
| 登入 | 直接簽 session cookie（等同 Google 登入成功後回到 `/`） | 沒走 Google 的畫面 |

**扮演的人物**：

- **Amy**：第一次來，從首頁 demo 開始，登入後建立輪盤，後來開成團隊輪盤
- **Ben**：Amy 的同事，用邀請連結加入
- **訪客**：沒有帳號，開公開連結 `/w/1`
- 另外兩個新帳號，用來走「拒絕定位」和「我想自己加店」兩條路線

**歷史資料**：在 Amy 的輪盤上灌了三週（9/3–9/23 的 15 個工作天、23 次轉動），刻意模擬真實情況。
大約一半是轉完直接按 Lock it in；約三成先重轉一兩次才決定；約兩成轉完**沒有人按 Lock it in**
（大家就直接去吃了）。另外有 9 個評分。

**這份報告是什麼、不是什麼**：這是**站在使用者位置的專家走查**，不是找真人來測。
「使用者會在這裡困惑」是判斷，不是觀察到的行為。每一項都標了證據等級（和 BACKLOG 相同）：

- **已驗證**：在瀏覽器裡實際操作、量測或截圖過
- **已確認**：讀過程式碼，邏輯確定，但沒有實際跑過
- **假設**：推論，需要真人或真資料才能確定

## 1. 使用者真正在意的是什麼

午餐輪盤的使用者，11:45 打開 app 時要解決的事情只有這幾件。拿首頁上的承諾來對照：

| 使用者在意的事 | 首頁怎麼說 | 實際上 | 落差 |
|---|---|---|---|
| **快點決定，而且大家服氣** | 「Nobody has to say "I don't mind" again」 | 轉盤本身又快又好看，結果有儀式感 | ✅ 沒問題 |
| **走得到、現在有開** | 「Every place carries its walk time」 | 用「Use my location」（主要按鈕）建立的輪盤**沒有步行時間**；快關門的店照樣可以被抽中 | ❌ P0-C、P1-M |
| **不要一直吃同一家** | 「Set your own no-repeat window」 | 只有按了 Lock it in 才排除 3 天；按 Directions 直接出發、或關掉結果，**只排除今天** | ❌ P0-B |
| **全隊都知道今天吃什麼** | 「everyone watches the same result land」 | 隊友的輪盤不會動，只收到一個 toast；決定之後畫面上找不到今天的結果；兩個人可以各自鎖定不同的店 | ❌ P0-A、P0-D |
| **有人不吃牛、不吃辣** | 「mark it once and it stops coming up」 | 靠料理標籤運作，但**從 Google 加的店都沒有標籤**，所以標了也沒用 | ❌ P1-K |
| 事後：**最近吃過什麼、哪家好吃** | （沒有承諾） | 紀錄頁記的是「轉了什麼」，不是「吃了什麼」 | ⚠️ 第 5 節 |

## 2. 最大的問題（P0：主線上的承諾沒有兌現）

### P0-A 決定完就消失：app 沒有「今天吃這家」的狀態 — **已驗證**

- 按 Lock it in 之後，結果卡關閉，回到一個可以**再轉一次**的輪盤。畫面上沒有任何地方寫
  「今天：賢明茶館」（圖 3）。兩分鐘後想看一眼「剛剛是哪家？」，只能去紀錄頁往下捲。
- 團隊輪盤更明顯。12:10 Amy 鎖定賢明茶館，12:22 Ben 加入後看到的是一個乾淨、隨時可以轉的輪盤，
  完全不知道已經決定了。他轉出這家炒飯也按了 Lock it in，於是**同一天有兩個「已決定」**。
  app 沒有提醒「Amy 已經鎖定賢明茶館」，Amy 只在鈴鐺裡收到「Ben Lin accepted Zhe Jia Fried Rice J+」。
- 使用者會怎麼想：「所以到底吃哪一家？」接著回到 LINE 群組吵，這正是這個產品要取代的東西。

**建議**：鎖定之後，輪盤頁的主角換成**今日卡片**：店名、步行時間、營業到幾點、Directions、誰鎖定的。
輪盤縮到下方，「重新決定」要多按一步。團隊輪盤上，當天已有鎖定時，再轉要先確認
（「Amy 12:10 已鎖定賢明茶館，要重新決定嗎？」）。**需要業主決定**：一天只能有一個決定，還是允許多個（例如分兩團）。

### P0-B app 不知道大家到底吃了什麼 — **已驗證 + 已確認**

「不重複」、紀錄、統計、公平模式、料理輪替，全部依賴 `accepted` 這個欄位，但它幾乎不可靠：

1. 結果卡在**還沒做任何決定時**就寫「We'll skip Song Wang Pork Knuckle for the next 3 days」（圖 2）。
   實際上只有按 Lock it in 才會是 3 天；按 Respin、關掉卡片、或只按 Directions，都只排除到**今天結束**
   （`WheelApp.tsx:805` 的註解：關掉 = 今天先跳過）。
2. 最自然的「我要去了」動作是按 **Directions**，但它不算接受。照著導航走去吃的人，明天那家店就會回到輪盤上，
   而且隊友不會收到通知。
3. 「Lock it in」這個按鈕沒有說明它會做什麼（排除 3 天 + 通知隊友）。沒有人會知道不按的後果。
4. 紀錄頁的說明文字「Restaurants are auto-excluded for 3 days after being spun」和畫面上的「11h left」互相矛盾。

**建議**：把「去吃了」變成**預設**，而不是額外的一步。按 Directions 就視為接受；
沒有 Respin 就關掉卡片，也視為接受（或過 30 分鐘自動接受）。Respin 繼續是「今天跳過」。
文案在決定前改成「Lock it in to skip it for 3 days」，或乾脆拿掉。
**需要業主決定**：自動接受的規則。

### P0-C 走主要路線建立的輪盤沒有步行時間 — **已驗證**（設計如此）

- 首次設定畫面每家店都有「2 min」「3 min」，但按「Use my location」建立的輪盤，資料庫裡
  `originLat = NULL`、`walkSeconds = NULL`、`distanceEnabled = 0`。店家頁沒有步行時間，
  輪盤頁也**沒有篩選按鈕**（沒有標籤、也沒開距離，所以 FilterBar 直接不顯示）。
- 原因是刻意的：「Only used for this search — it's never stored.」只有用搜尋選辦公室的路線才會存
  （`createFromNearby` 的 `origin`）。隱私承諾是對的，但結果是**最主要的按鈕**建出的輪盤，
  少了首頁第一個賣點，而且沒有任何提示告訴使用者可以補上。
- 要補回來，得找到：輪盤名稱 → ⋮ → Settings → Distance mode → Use my current location → Save。

**建議**：建立完成時問一句「把這裡存成辦公室？步行時間會一直顯示」［存］［不要］。
這是明確同意，隱私承諾還在。**需要業主決定**。

### P0-D 「大家一起看到結果落下」沒有發生，而且 toast 會先爆雷 — **已驗證**

- Ben 按下開轉，Amy 的輪盤完全不動。**1.5 秒後** Amy 收到 toast：「Ben Lin spun Zhe Jia Fried Rice J+」（圖 4），
  這時 Ben 的輪盤還在轉（大約 5 秒才停）。坐在隔壁的兩個人，看的人比轉的人先知道答案。
- 程式裡沒有「同步觀看轉動」的功能，只有 `app.realtime.spin` 的 toast（`WheelApp.tsx:615`）。
- 首頁第三個賣點「Share one link and everyone watches the same result land」目前不成立。

**建議**：短期把 toast 延後到轉的人那邊落定之後（server 知道 decay 的長度）。
或者 toast 只寫「Ben 正在轉…」，點開後在自己的輪盤上**重播**同一個落點。長期才是真正的同步。
如果不打算做，就改首頁文案。**需要業主決定**。

## 4. 小問題（P2）

**表單與可及性**

- 建立／設定輪盤對話框：點「Add starter restaurants」這些文字**不會**切換開關（label 沒有連到 switch）。
  開關只有 18px 高，所以只能點那個小開關。
  「Fairness mode」「Rotate cuisines」「Distance mode」沒有任何說明。**已驗證**
- 設定對話框一打開，就自動聚焦輪盤名稱並**全選**（圖 10）：手機上鍵盤直接跳出來，打錯一個字就蓋掉名稱。**已驗證**
- 「Add nearby」對話框也是打開就聚焦輸入框，而且輸入是選填的，但沒有自動列出結果，要先按那個沒有標籤的搜尋圖示。**已驗證**
- 無文字按鈕：店家頁的「＋」、搜尋圖示、邀請連結的複製按鈕、投票／否決，只有 `title` 或完全沒有標籤。
  Console 另有一個 Dialog 缺 `DialogTitle` 的錯誤。**已驗證**

**建立與範例**

## 5. 紀錄頁（History）對使用者有沒有意義？

**結論：有一半有意義，但使用者最想看的那一半放在最下面，而且資料是錯的。**

三週資料下，紀錄頁由上到下是（圖 7、8）：統計磚 → 該回訪了 → 最常轉到 → 誰在轉 → 團隊口味 →
團隊最愛 → 轉動紀錄（23 列）。要捲大約 1300px 才看到第一筆紀錄。

| 區塊 | 使用者會拿它做什麼 | 問題 | 建議 |
|---|---|---|---|
| Total spins **23** | 什麼都不會做 | 虛榮數字；而且包含重轉 | 刪掉，或改成「決定了 15 天午餐」 |
| Places tried **12/12** | 「還有哪些沒去過？」 | **錯的**：把重轉掉、沒去的也算成「去過」。三週裡實際鎖定過的只有 8 家（八方雲集只被重轉掉過一次，從沒去過） | 「去過 8／12」，並列出沒去過的 4 家 |
| Favourite: **Zhe Jia** | 「我們最喜歡哪家？」 | 誤導：用**被轉到的次數**當「最愛」，但輪盤是隨機的，次數是運氣。同一頁的「Team favourites」又用評分算出另外三家，兩個「最愛」互相矛盾 | 刪掉，最愛只看評分 |
| Due for a comeback | 「好久沒吃火鍋了」 | **最有用的一塊**，但 chip 不能點，只有建議沒有動作 | 點了就「今天加權」或「直接去這家」 |
| Most picked | — | 隨機的次數＝雜訊；而且是「該回訪了」的反面，重複 | 刪掉 |
| Who's been picking | 「誰都在負責按按鈕」 | 誰按按鈕不重要（決定的是輪盤），而且重轉也算 | 刪掉，或低調放到團隊頁 |
| Team taste / Team favourites | 「哪家大家都說好吃」 | **有意義**，而且評分真的會讓好店常出現，但頁面沒說 | 保留，加一句「評分高的店會更常轉到」 |
| Spin history（23 列） | 「上次去鵝肉担是什麼時候？」「這週吃了什麼？」 | 使用者最想看的東西，卻放在最底下。只有「14d ago」沒有日期；沒有按天分組；重轉的和真的去吃的混在一起，看不出 9/15 最後吃了哪家（八方、鵝肉、定盒所三列都寫「9d ago · by Ben Lin」）；列號 1–23 沒有意義；有些列能評分、有些不能（只有每家最新的一列可以），規則看不出來 | 改成**午餐日記**：一天一列「週二 9/15 · 定盒所 · Ben 鎖定」，重轉掉的店用小字附在下面，依週分組；評分放在日記那一列 |

**使用者真的在意、而頁面沒有回答的問題**：

1. 「這週吃了什麼？」（按天，不是按次）
2. 「上次去 X 是什麼時候？」（日期，不是 14d ago）
3. 「有哪些我們喜歡、但好一陣子沒去的？」（該回訪了 × 評分）
4. 「還有哪些根本沒試過？」
5. 「每週吃飯花多少？」（目前沒有資料，低優先）

**根本原因還是 P0-B**：只要 app 不知道「吃了哪家」，這一頁的每個數字都會把重轉和沒去的算進去。
先修資料（去吃了 = 預設；隔天確認並評分），再重排這一頁：日記放最上面，統計縮成一行摘要。

## 6. 還沒被解決的痛點（產品層面）

1. **一個全隊共享的「今天」**：今天決定了沒、決定了哪家、誰要一起去、幾點出發。
   目前沒有任何一個畫面回答這個問題。
2. **把人叫過來**：11:45 做決定時，不在 app 裡的隊友不會知道，因為通知只有 app 內的鈴鐺，而且 15 秒輪詢一次。
   結果卡上沒有「分享到 LINE」。真實的團隊會把結果截圖貼到 LINE。
3. **時間這個維度**：幾點關門、走到的時候還開不開、午餐尖峰要排多久。
   目前只有「open / closing soon / closed」，而且不影響能不能被抽中。
4. **長期的飲食限制**：「我不吃牛」是一個人的屬性，不是「這一輪」的屬性。
   目前放在 This round 裡，依賴從 Google 加的店都沒有的標籤。
5. **「去了沒」的回饋迴圈**：app 不問，所以不知道；不知道，所以排除、公平、輪替、紀錄、統計都失準。
   這是產品裡最便宜、影響最大的一個問題：下次打開時問一句「昨天去賢明茶館了嗎？★★★★☆」。
